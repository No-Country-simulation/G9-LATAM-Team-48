## 1. Que se implemento

- **Mensajes traducidos** para las recomendaciones energeticas en tres idiomas:
  espanol (`es`), ingles (`en`) y portugues (`pt`).
- **Resolucion dinamica de idioma** por peticion, a traves de `MessageSource`
  de Spring y el `Locale` activo del hilo (`LocaleContextHolder`).
- **Mensaje de contingencia** (`recommendation.default`) tambien traducido,
  usado cuando ninguna regla de negocio aplica al perfil evaluado.
- **Cero texto de usuario final hardcodeado** en las clases de reglas
  (`HighConsumptionRule`, `MediumConsumptionRule`, `LowConsumptionRule`): todo
  el contenido visible para el usuario vive en los archivos de propiedades.

> El feature aplica hoy unicamente al modulo `recommendation`. Los mensajes de
> error de validacion, autenticacion, etc. no estan alcanzados por este
> trabajo (ver seccion 10).

---

## 2. Justificacion: por que i18n

El proyecto tiene alcance regional (LATAM, con origen de la consigna en
portugues de Brasil) y el frontend puede servir usuarios en distintos idiomas.
En ese contexto se eligio desacoplar los textos del codigo en lugar de
hardcodearlos por dos razones principales:

- **Principio SRP/OCP (SOLID):** si el texto de una recomendacion vive dentro
  de la regla de negocio (`HighConsumptionRule`), la clase mezcla dos
  responsabilidades (decidir *si* aplica y *que* decir) y cualquier cambio de
  redaccion o un nuevo idioma obliga a modificar codigo Java ya compilado.
  Externalizar el texto separa esas responsabilidades y permite anadir un
  idioma nuevo sin tocar ninguna regla existente.
- **Alcance regional real:** LATAM + Brasil conviven en el mismo proyecto; que
  el mismo backend responda en `es`, `en` o `pt` segun el cliente evita
  mantener forks o condicionales de idioma dispersos en el codigo.

## 3. Beneficios

| Beneficio           | Detalle                                                                |
|---------------------|--------------------------------------------------------------------------|
| Desacoplamiento     | Las reglas de negocio (`RecommendationRule`) no conocen el idioma final. |
| Extensibilidad      | Sumar un idioma es agregar un archivo `.properties`, sin tocar Java.     |
| Mantenibilidad      | Un traductor o no-programador puede editar los mensajes sin riesgo.      |
| Testeabilidad       | Se verifica con `ResourceBundleMessageSource` real, sin mockear texto.   |
| Estandar de Spring  | Usa `MessageSource` + `LocaleContextHolder`, sin dependencias externas.  |

## 4. Diseno y componentes

| Componente | Paquete / ubicacion | Responsabilidad |
|------------|----------------------|------------------|
| `messages_es.properties` | `src/main/resources` | Mensajes en espanol (idioma por defecto del bundle). |
| `messages_en.properties` | `src/main/resources` | Mensajes en ingles. |
| `messages_pt.properties` | `src/main/resources` | Mensajes en portugues. |
| `MessageSource` | Bean estandar de Spring Boot | Resuelve una clave (ej. `recommendation.high.consumption`) al texto del idioma activo. |
| `LocaleContextHolder` | `org.springframework.context.i18n` | Expone el `Locale` activo del hilo actual (via `ThreadLocal`). |
| `HighConsumptionRule` / `MediumConsumptionRule` / `LowConsumptionRule` | `recommendation.rules` | Reciben `MessageSource` por constructor y lo usan en `evaluate()` para resolver su mensaje, sin texto hardcodeado. |
| `RecommendationServiceImpl` | `recommendation.service` | Resuelve el mensaje de contingencia (`recommendation.default`) via el metodo privado `resolveDefaultMessage()`. |

**Decisiones de diseno relevantes:**

- Las claves siguen la convencion `dominio.subdominio.detalle`
  (ej. `recommendation.high.consumption`), consistente entre los tres
  archivos de idioma.
- `messages_es.properties` actua como *bundle por defecto* (sin sufijo de
  idioma en el nombre base `messages`): si Spring no encuentra el idioma
  solicitado, cae en este archivo (ver seccion 8).
- Cada regla recibe el `MessageSource` **inyectado por constructor**, no como
  campo estatico ni via `@Autowired` de campo — mantiene las reglas
  testeables de forma aislada (ver seccion 9).

## 5. Flujo de resolucion de idioma

```
Peticion HTTP                              Generacion de recomendacion
──────────────                             ────────────────────────────

Cliente                                    RecommendationServiceImpl
  │  Header: Accept-Language: pt-BR          │
  ▼                                          ▼
Spring MVC (AcceptHeaderLocaleResolver*)   regla.evaluate(request)
  │  Resuelve Locale = "pt"                  │
  │  LocaleContextHolder.setLocale(pt)       │  messageSource.getMessage(
  ▼                                          │      "recommendation.high.consumption",
Controller invoca al servicio                │      null,
  │                                          │      LocaleContextHolder.getLocale()
  ▼                                          │  )
generate(RecommendationRequest)              ▼
                                            "Seu consumo de energia e alto..."
```

`*` `AcceptHeaderLocaleResolver` es el resolvedor **por defecto implicito** de
Spring MVC (`DispatcherServlet`) cuando no se registra un bean `LocaleResolver`
propio. Lee el header estandar `Accept-Language` sin configuracion adicional.
Ver seccion 10 sobre por que conviene declararlo explicitamente.

## 6. Configuracion

No requiere variables de entorno. La configuracion vive en el nombre y
contenido de los archivos de propiedades:

| Archivo | Idioma | Bundle base |
|---------|--------|--------------|
| `messages_es.properties` | Espanol (default) | `messages` |
| `messages_en.properties` | Ingles | `messages` |
| `messages_pt.properties` | Portugues | `messages` |

El `basename` (`"messages"`) es el que se usa al construir el
`ResourceBundleMessageSource` (ver seccion 9 para el caso de test; en la
aplicacion real, Spring Boot lo autoconfigura a partir de
`spring.messages.basename`, que por defecto ya es `messages`).

## 7. Uso

> El modulo `recommendation` aun no tiene un endpoint HTTP propio (no existe
> `RecommendationController` a la fecha de este documento). Se usa hoy
> exclusivamente desde el service, invocado de forma programatica o desde
> tests. Esta seccion documenta el uso esperado una vez expuesto por HTTP.

### 7.1 Uso esperado via API (cuando exista el controller/orquestador)

```bash
curl -X POST http://localhost:8080/api/v1/analisis-energetico \
  -H "Content-Type: application/json" \
  -H "Accept-Language: pt" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"consumo_kwh": 420, "uso_horario_pico": true, ...}'
```

El header `Accept-Language` determina el idioma de las recomendaciones en la
respuesta, sin necesidad de ningun parametro adicional en el body.

### 7.2 Uso programatico actual (desde otro componente Spring)

```java
RecommendationRequest request = new RecommendationRequest(
        "user-123", "ALTO", null, null, null, null, false);
RecommendationResponse response = recommendationService.generate(request);
// El idioma resuelto depende del LocaleContextHolder activo en el hilo actual.
```

## 8. Manejo de casos sin traduccion

| Situacion | Comportamiento |
|-----------|----------------|
| Idioma solicitado no soportado (ej. `fr`) | Cae al bundle por defecto (`messages_es.properties`, espanol). |
| Categoria de consumo sin regla que aplique | `RecommendationServiceImpl` devuelve el mensaje `recommendation.default`, tambien traducido segun el `Locale` activo. |
| Clave de mensaje inexistente en el `.properties` | `MessageSource.getMessage()` lanza `NoSuchMessageException` en tiempo de ejecucion — no hay fallback automatico a un texto generico. Cubrir con tests (seccion 9) es la mitigacion actual. |

## 9. Pruebas

`RecommendationServiceImplTest` verifica el comportamiento de extremo a
extremo del motor de reglas junto con la resolucion real de traducciones:

- Genera un `ResourceBundleMessageSource` de prueba apuntando al mismo
  `basename` (`"messages"`) que usa la aplicacion — se testea contra los
  `.properties` reales, no contra mocks de texto.
- Un test por idioma/categoria: alto consumo en espanol, medio en ingles, bajo
  en portugues.
- Un test del mensaje de contingencia (`recommendation.default`) para
  categoria desconocida.
- `@AfterEach` con `LocaleContextHolder.resetLocaleContext()`: evita que el
  `Locale` seteado en un test se filtre al siguiente (el `Locale` vive en un
  `ThreadLocal` que JUnit no resetea solo).

Ejecucion:

```bash
cd backend
mvn test -Dtest=RecommendationServiceImplTest
```

## 10. Limitaciones actuales y mejoras futuras

**Limitaciones (estado actual):**

- No hay un bean `LocaleResolver` declarado explicitamente: se depende del
  default implicito de Spring MVC (`AcceptHeaderLocaleResolver`). Funciona,
  pero no es explicito ni configurable (ej. no hay lista de idiomas
  soportados ni un idioma por defecto declarado en codigo). Un bean explicito
  documenta la decision en el propio codigo, en lugar de depender de que
  quien lea el proyecto conozca el comportamiento default de Spring MVC.
- No existe aun `RecommendationController`: el modulo no es alcanzable por
  HTTP, solo probado via tests unitarios y uso programatico directo.
- Los mensajes de error de validacion, autenticacion y otras respuestas de la
  API **no** estan internacionalizados — el alcance actual es unicamente el
  texto de las recomendaciones.
- Sin un idioma solicitado invalido o no soportado, no hay registro (log) de
  que se aplico el fallback a espanol; es silencioso.

**Mejoras futuras:**

- Declarar explicitamente un bean `LocaleResolver`
  (`AcceptHeaderLocaleResolver` con `setDefaultLocale(Locale.of("es"))` y una
  lista de `supportedLocales`), para dejar el comportamiento documentado en
  codigo en lugar de depender del default implicito de Spring.
- Extender i18n a `GlobalExceptionHandler` (mensajes de error) y a las
  validaciones de Bean Validation (`@NotNull`, etc.), reusando el mismo
  `MessageSource`.
- Cuando se defina el `RecommendationController` (o el orquestador que
  combine `prediction` + `recommendation`), documentar el header
  `Accept-Language` en la anotacion Swagger/OpenAPI del endpoint.
- Si `RecommendationRequest` se amplia con variables crudas de consumo (ver
  discusion pendiente en el sprint), evaluar si las nuevas reglas especificas
  (ej. horario pico, cantidad de equipos) requieren claves de mensaje
  adicionales en los tres idiomas.

## 11. Deprecacion (actualizacion posterior)

Esta implementacion de i18n (mensajes completos pre-traducidos via
`MessageSource`) quedo **deprecada** tras acordar con el equipo que el
frontend maneja su propia traduccion de claves cortas (consistente con el
vocabulario `tipKeys` ya usado en el resto del sistema). El feature de
internacionalizacion **no desaparece** — se sigue soportando ES/EN/PT —
pero el mecanismo cambia: `recommendation` ahora devuelve identificadores
cortos (ej. `"peak"`, `"ac"`, `"led"`) en lugar de oraciones ya traducidas,
y es el frontend quien resuelve el texto final segun el idioma activo de
la UI. Los archivos `messages_es/en/pt.properties` y el uso de
`MessageSource`/`LocaleContextHolder` en `RecommendationServiceImpl` y las
reglas quedan sin uso a partir de este cambio.
